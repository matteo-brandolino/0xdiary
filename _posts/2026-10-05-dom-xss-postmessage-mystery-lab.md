There was nothing to type into. No search box, no comment form, no parameter I could see changing anything on the page. The lab was one of the two categories I'd put in my pool, DOM or XSS, and the page gave me nothing to put a canary into. So I stared at an empty shop and thought: if there's nothing to type into, the input has to be somewhere I can't type.

The lab came from [Mystery Pool]({% post_url 2026-10-04-mystery-pool %}), the tool I built to roll a lab from only the topics you choose. I had picked DOM and XSS, and PortSwigger doesn't tell you which one you got. That's the whole point of a mystery lab.

## Setup: a shop with no inputs

The lab is called "Mystery challenge" and it's a small online shop selling crochet gift wrapping. I had Burp Suite running, the DOM Invader extension (version 2.0.11) in Chrome, and the browser pointed at the Burp proxy. Nothing clever yet. I wanted to know where the page's data came from before deciding what kind of bug I was looking at.

## 1. An empty page is still a clue

If a page has no visible input, whatever it reads comes from somewhere the user doesn't see: the URL hash, a query parameter no form exposes, `window.name`, or a message from another window. That narrowed the search, but it didn't decide it. A reflected XSS needs the server to echo something back, and I couldn't find anything for the server to echo. So the bet went on the JavaScript, and DOM Invader was the tool to check the bet.

## 2. Zero is not a verdict

DOM Invader's first screen showed two counters at zero: DOM 0 and Messages 0. The canary was `zgrucnap`, and a warning at the bottom said only interesting sinks were being shown, with all sources hidden. Zero sinks doesn't mean the page is safe. It means the canary never reached a sink. The next question was whether the canary was ever sent anywhere, so I turned on postMessage interception and reloaded.

## 3. A message from a host that doesn't exist

After the reload, Messages showed one result. Its origin was `https://0a4e…web-security-academy.net.fakeweb-security-academy.net`. That isn't a real origin, and for a moment it looked like evidence: something on the page was sending messages from a host that didn't belong to it.

I checked the settings. Postmessage origin spoofing was on, and so was "Generate automated messages". DOM Invader had created that message itself, as a test, and the fake origin was its own work. I turned both off and reloaded. Messages was empty. On its own, the page sent nothing.

The lesson is about which traffic you're reading. A test generated by the tool and a message sent by the page look the same in the list. The origin was the only clue, and I only saw it because I went back to the settings. From then on I turned the test features off before reading anything.

## 4. The listener belongs to one page

An empty Messages list meant the page was waiting for something from outside. So I went looking for the listener itself. In Burp's HTTP history, the response to `GET /` contains an inline script with `window.addEventListener('message', ...)`. The same string isn't in the response for the product page.

A listener belongs to the page that registers it, not to the whole site. The home page and the product page don't run the same script, and a search that only checks one of them can tell you the wrong story.

## 5. The scanner had nothing to say

A Burp scan on `GET /` came back empty, and once I thought about it, that made sense. The request has no parameters for the scanner to put payloads into. The data in this bug never travels in an HTTP request: it arrives as a message from another window and gets handled in the browser. An empty report here doesn't mean the page is clean. It means the scanner had no path to the sink.

## 6. Four lines that decide everything

This is the part of the listener that matters:

```javascript
window.addEventListener('message', function(e) {
    ...
    d = JSON.parse(e.data);      // checks the shape of the message
    switch(d.type) {
        case "load-channel":
            ACMEplayer.element.src = d.url;   // the sink
            break;
    ...
```

The `try/catch` around `JSON.parse` and the `switch` on `d.type` both look like validation, and both check the shape of the message. Neither checks who sent it. There's no `e.origin` anywhere in the function. Then `d.url` goes straight into `iframe.src`. An iframe whose `src` is a `javascript:` URL runs that code with the origin of the page that set the `src`, and here that page is the lab, because the lab's own listener set it.

## 7. The objective, and the payload

The objective was `print()`. I got it by clicking "Reveal objective" on the lab page, because nothing else in the page would have told me what the lab wanted. Once I had it, the payload had two jobs: send a `load-channel` message to the listener, and put a `javascript:` URL in the field it reads.

The exploit server body:

```html
<iframe src="https://YOUR-LAB-ID.web-security-academy.net/" onload="this.contentWindow.postMessage(JSON.stringify({type:'load-channel',url:'javascript:print()'}),'*')"></iframe>
```

Each detail is there for a reason:

- **`onload`.** The listener exists only after the lab's home has loaded. A message sent earlier goes nowhere.
- **`JSON.stringify`.** The listener calls `JSON.parse(e.data)`. An object would fail the parse and hit the `return`, and nothing would happen.
- **`'*'` as the target origin.** This lets the message reach a window from a different origin. That's allowed by design. The receiver is the one that should check who is sending.

I stored the exploit, delivered it to the victim, and the lab changed to solved.

## The pattern underneath

A check on the shape of a message is not a check on its sender. The `try/catch` and the `switch` made the listener look careful, and they were careful about the wrong thing. The message format was the only thing it validated.

Both the zero counters and the empty Messages list were true, and neither told me anything until I knew what the page itself sends. A tool that shows you traffic is only as useful as your knowledge of which traffic is yours.

## Exam and field

| | Exam | Field |
|---|---|---|
| What to recognise | a `message` listener with no `e.origin` check, feeding a sink | the same pattern in widgets, video players, chat embeds, and third-party iframes |
| Where the time goes | delivery: `onload`, JSON shape, the `javascript:` scheme | finding out what the logged-in user can do on the target site |
| Common trap | a perfect payload sent before the listener exists | assuming a victim must visit a link, when a page the victim already trusts can host the frame |
| Real limit | a single objective, here `print()` | the victim must visit the attacker's page; if the target blocks framing, the attacker can use `window.open` and keep the same message |

On the exam, the payload is the easy part. The bug is in the delivery, and a single misplaced `onload` makes a working exploit look broken.

In the field, the same listener gives an attacker code running as the logged-in user on the target site. A `HttpOnly` cookie can't be read from the script, but requests made from that origin still carry it. CSRF tokens in the DOM are readable. Whatever the user can do on that site, the script can do too.

The defence is one check: compare `e.origin` against a list of expected origins before touching `e.data`. The second rule is to never pass a value from a message into `iframe.src`, or to accept only `https:` URLs from a list of hosts.

## What comes next

The fake origin DOM Invader generated, `…net.fakeweb-security-academy.net`, has exactly the shape a loose origin check accepts. A check that asks whether the origin *ends with* `web-security-academy.net` would let it through, because nothing requires the dot before the domain. This lab had no check at all, so I couldn't test that. It's the next thing to try on a lab that has one, and it's the same question as the [cookie lab]({% post_url 2026-10-01-dom-cookie-manipulation-mystery-lab %}): what does the page believe about where its data came from?

## Takeaways

- A listener without an origin check accepts input from any page on the internet.
- An empty Messages list means the page sends nothing on its own. It doesn't mean nothing reaches the page.
- A check on the message format is not a check on the sender.
- Scanners test what travels in HTTP requests. A `postMessage` never does, so the scanner's empty report tells you nothing about the page.
